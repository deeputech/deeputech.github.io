I recently posted on my blog and Reddit about my experience pitting Qwen 3.8 Flash-Next against Claude Opus in some tasks and some people on Reddit pointed out that it wasn’t a fair comparison since I used different harnesses and thinking effort levels. So I did a more controlled comparison to see how they truly stack up against each other. It’s still a non-deterministic comparison, but it provides a clearer picture of how they measure up against each other.

You can read the previous comparison in the blog below and on Reddit.

Agentic coding on a Strix Halo laptop with Qwen3.8-Flash-Next. Going head to head with Opus 5.5

#ai#qwen38flashnext#localllm#qwen38#claudeopus

TL;DR

  • All 12 runs finished the task, and all 12 PRs passed the end-to-end test.
  • Flash-Next took 1.1x to 2.1x as long as Opus 5.5 at the same effort (set 2).
  • Average score, out of 8:
    • Claude Code + Opus 5.5 - 6.59 (82%)
    • Claude Code + Flash-Next - 5.44 (68%)
    • Pi + Flash-Next - 5.25 (66%)
  • With Flash-Next, Claude Code and Pi scored the same on the review questions. CI passed on 4 of 4 Claude Code + Flash-Next PRs and 1 of 4 Pi PRs. Claude Code was also faster in the cleaner set, though Flash-Next had to answer its auto mode tool checks too.
  • Opus xhigh scored 6.94 against 6.25 for medium, at 2.7x the cost. Flash-Next medium and xhigh scored almost the same.
  • At API prices, a set 2 Opus run cost $6.52 (medium) or $17.78 (xhigh), and a Flash-Next run $0.32 to $0.67.

Combinations compared

I wanted to compare both harness differences and thinking effort differences so I decided to set up a six-way comparison with the help of Claude Code + Opus 5.5.

Each combination ran twice: once where the agent measured save and restore at 100k tokens itself (set 1), and once with those numbers given in the prompt (set 2). Total 12 runs.

Opus 5.5 is a frontier cloud model with more than a trillion parameters, and Anthropic doesn’t publish its actual size. Qwen3.8-Flash-Next is a mixture of experts model with 125B parameters, 6B active per token and a 51B n-gram embedding, and it runs on my laptop at ~Q4 quantization.

The Task

I picked a real feature from the LlamaStash roadmap. LlamaStash unloads a model when it needs room for another one or when it has been idle too long, and the next request then has to reprocess the whole prompt. llama-server can save a slot’s KV cache to disk and load it back, so the task was to save the cache before an unload and restore it when the model comes back.

The agent had to measure save and restore at 100k tokens first (a spike), design the caps, cleanup and cache matching, prove it works end to end, add tests and docs, and open a PR.

The full prompt for the first set

How I Ran It

An orchestrator session (Claude Code + Opus 5.5) started each run and collected the numbers. Every run got a fresh clone of LlamaStash at the same commit, the same prompt, a 3 hour limit and one “continue” if it stopped early. Claude Code ran in auto mode, which sends its tool checks to the same model, and Pi ran with its guard off. The PRs are in a public scratch repo, deepu105/llamastash-b4r2.

The agents, builds and tests ran on my Dell XPS 15. Flash-Next was served from my ASUS ROG Flow Z13 (Strix Halo, 128GB) by LlamaStash via Halogen, over the LAN.

In the first set, each agent ran the 100k-token spike itself on the XPS CPU, which took 48 to 53 minutes per run. This was a mistake, it should have used the GPU, and by the time I noticed all six runs finished and since quality won’t depend on the spike I decided not to redo them. In the second set, the spike numbers were in the prompt and llama-server ran on the GPU.

Scoring

Each PR got seven review questions and a CI check, for a maximum score of 8:

  • Q1: Is a restore into a different model or launch config refused?
  • Q2: Are the save files capped and cleaned up?
  • Q3: Is the eviction code still backend neutral? LlamaStash’s AGENTS.md doesn’t allow llama.cpp names in generic code.
  • Q4: Do the tests run the new code?
  • Q5: Are the docs, config example and CHANGELOG updated and correct?
  • Q6: Does the PR avoid changes the task didn’t ask for?
  • Q7: Is the eviction safe? It should check for new requests after the save, and block a second eviction of the same model during the save.
  • CI: Do the PR’s tests pass on all platforms?

Each answer gets the grade of its worst problem:

GradeProblemExamples
1none
0.75lowa comment naming llama.cpp in generic code, a missing README row, an untested edge case
0.5mediuma wrong cache restored in a rare setup, a request cut off in a rare race, a doc that describes the wrong behaviour, untested core paths
0.25higha wrong answer or a cut-off request in normal use

For CI, a failing test that the PR added for working code gets 0.75. That includes two tests that hang on Windows, since the hang could be in the test rather than the code.

Four scorings went into the final score. Pi + Flash-Next and Claude Code + Opus 5.5 scored the PRs first. A second Claude Code + Opus 5.5 session checked every place they disagreed in the code and graded each problem by severity. Then Kimi K3 (in GitHub Copilot CLI) scored all 12 PRs on its own, without knowing which run made which PR. The final score is the average of these last two, except where Kimi missed something that was checked in the code. There the Opus grade is used.

Results

Did They Finish?

Yes. All 12 runs opened a PR, and all 12 PRs pass the end-to-end test. After LlamaStash unloads the model, the follow-up prompt gets 15,000 tokens from the restored cache and takes about 1.4 s, against 5.2 to 6.1 s without the feature. One Flash-Next run needed the “continue”.

What Opus did and Flash-Next didn’t

  • A request during the save: The Opus PRs check for new requests after the save. The Flash-Next PRs don’t, so a request that arrives during the save (under a second) gets cut off.
  • Two evictions at once: Only the Opus xhigh PRs block a second eviction while the first one is still saving.
  • Cache matching: The Opus PRs key the cache on the full launch command and the model file. The Flash-Next PRs key on less, 3 of them on the model path only, so a relaunch with different flags can restore an old cache.
  • Tests: The Opus PRs and 2 Pi + Flash-Next PRs test save and restore through the eviction code. The other 6 Flash-Next PRs have unit tests only.
  • Docs: 4 Flash-Next PRs have a doc that describes something the code doesn’t do.

What Flash-Next did and Opus didn’t

  • CI: All 4 Claude Code + Flash-Next PRs passed on every platform. Opus medium #2 failed on Windows.
  • SECURITY.md: Pi + Flash-Next xhigh #6 added a SECURITY.md note, since the feature writes conversation tokens to disk and turns on llama-server’s slot endpoints. Opus #2 and #11 didn’t.
  • Tests: Pi + Flash-Next #3 and #12 scored a bit higher on tests than the Opus medium PRs #2 and #8, which don’t test their own check for requests that arrive during the save.
  • Scope: Claude Code + Flash-Next #5, #10 and #13 made no unrelated changes. Opus xhigh #4 left an unused function behind.
  • Smaller PRs: The Claude Code + Flash-Next PRs added 867 to 1,223 lines, against 1,373 to 2,729 for Opus. Not scored.
  • On by default: 7 of 8 Flash-Next PRs turn the feature on by default, against 2 of 4 Opus PRs. That saves a config step, but I didn’t score it either way.

So Opus was ahead on the parts that change what a user gets: cache matching and eviction safety. Flash-Next did better only in some PRs, on CI, docs, tests and scope.

Claude Code vs Pi for Flash-Next

This was surprising for me, since Pi is my daily driver. Both scored the same on the review questions, and Claude Code was ahead on CI.

Claude Code also sent its auto mode tool checks to the same Flash-Next server, 22 to 79 per run, which took 10 to 14% of the run time. Pi sent none. Claude Code + Flash-Next was still faster than Pi in both set 2 pairs (by 6% and 22%). In set 1, Pi was faster in both (by 18% and 3%).

Three of the 4 Pi PRs fail the Windows test jobs, and no pre-push hook covers Windows. With one run per combination per set, I wouldn’t read too much into it.

Medium vs xhigh

For Opus, xhigh scored higher in both sets (6.63 against 6.0, and 7.25 against 6.5), and only the xhigh PRs block two evictions at once. But it cost 2.6x to 2.7x as much and took 43.5 minutes against 23.4 in set 2.

For Flash-Next, medium and xhigh scored almost the same (5.28 and 5.41), and xhigh was slower in all 4 pairs. I have been running Flash-Next at xhigh, and on this task it didn’t help.

The Reviewers

Flash-Next, Opus and Kimi K3 all scored these PRs, so they can be compared as reviewers too:

  • Flash-Next found the “request during the save” problem in 2 of the 8 Flash-Next PRs and no llama.cpp names in generic code. Opus found the first in all 8 and the second in 6.
  • Opus missed that 3 PRs left their new config key out of the README.
  • Kimi K3 gave the same grade as Opus on 63 of 84 answers and was never stricter. It missed the four docs that describe the wrong behaviour.

In the previous post, I said Flash-Next’s reviews found more issues than Opus’s. On this task it was the other way around.

Caveats

  • Biggest caveat is that the models are not on the same league. Opus is a frontier model run at FP16 or atleast FP8. I ran Flash-Next on my laptop at 4.16 bpw (experts and the rest: 4-bit, the mixing layers: 6-bit, draft head: 8-bit, n-gram lookup table: FP8). Flash-Next at FP8 should show a bit more quality.
  • One run per combination per set, so I don’t know how much the results vary from run to run.
  • The end-to-end test used a 1B model at 15k tokens.
  • The two save-race problems were found by reading the code, not reproduced.
  • The sets differ in the prompt (do spike vs spike data given) and the llama-server build (CPU against GPU).
  • All the scorers are LLMs, and the session that settled their disagreements ran on Opus.
  • The machine running Flash-Next ran at 70W TDP ceiling for the entire duration. I could have run it at 90W for slightly better speed but the fan noise and thermal stress was not worth it.

Final Thoughts

With the harness and effort kept the same, Opus 5.5 wrote better code than Flash-Next on this task and finished sooner. This was expected of course from a frontier model. That’s different from my previous post, where I liked Flash-Next’s PR better than the one from Opus at medium effort.

But Flash-Next was right behind in scores and time, and the gap wasn’t that wide. Opus is a frontier model on Anthropic’s servers, and Flash-Next has 6B active parameters and runs on my laptop. It finished every run, every PR works, it took 1.1x to 2.1x as long, and it cost me only electricity. What it missed (the save race, cache matching, integration tests, docs) is what a review catches, and that is how I already use it: an orchestrator plans and reviews, and Flash-Next does the implementation.

Two things I’ll try in my work. I’ll run Flash-Next at medium instead of xhigh, and I’ll give Claude Code + Flash-Next a proper try instead of using only Pi, and see how both go.

All 12 PRs are in deepu105/llamastash-b4r2 if you want to read the code yourself.
